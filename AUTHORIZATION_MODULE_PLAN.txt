Authorization Module Deepening Implementation Plan
================================================

## Design Decisions Summary

### Module Structure
- Location: src/auth/authorization/
- Sub-modules: TokenValidation, RoleExtraction, PermissionChecking, SessionManagement
- Main interface: createAuthorization(tokenValidator, permissionChecker)
- Pattern: Functional composition with dependency injection

### Key Interfaces
- TokenValidator: validate(token: string): Promise<Identity | null>
- PermissionChecker: checkPermission(identity: Identity, permission: string): boolean
- Identity: { id: string; email: string | null; role: AdminRole }

### Integration Strategy
- Legacy compatibility: Wrappers in existing files (api/_authorization.ts, api/_auth.ts)
- Migration: Incremental - one API handler at a time
- Error handling: Custom errors (UnauthorizedError, ForbiddenError)

### Testing
- Unit tests: src/auth/__tests__/unit/ for each sub-module
- Integration tests: src/auth/__tests__/integration/
- Mock adapters: Factory functions in test helpers

### Documentation
- JSDoc comments on functions/interfaces
- Separate AUTH_MODULE.md documentation

## Migration Plan

### Phase 1: Module Creation
1. Create all module files without touching existing code
2. Implement unit tests and ensure they pass
3. Create documentation

### Phase 2: Legacy Wrappers
1. Implement wrappers in api/_authorization.ts
2. Implement wrappers in api/_auth.ts
3. Ensure existing tests still pass

### Phase 3: Incremental Migration
1. Choose one API handler (e.g., admin overview)
2. Migrate to use new module directly
3. Test thoroughly
4. Repeat for other handlers

### Phase 4: Cleanup
1. Remove legacy wrappers
2. Update documentation
3. Final testing

## Key Benefits

1. **Locality**: All authorization logic centralized in one module
2. **Leverage**: Reusable authorization logic across different contexts
3. **Testability**: Seams allow comprehensive testing without HTTP coupling
4. **Maintainability**: Clear module boundaries and interfaces
5. **Flexibility**: Easy to swap implementations for different auth providers

## Risk Mitigation

1. **Backward Compatibility**: Wrappers ensure existing code continues to work
2. **Incremental Migration**: Migrate one handler at a time to reduce risk
3. **Comprehensive Testing**: Unit and integration tests ensure correctness
4. **Documentation**: Clear guides for migration and usage

## Success Criteria

1. All existing tests pass after module creation
2. Unit tests cover all sub-modules
3. Integration tests cover full authorization flow
4. At least one API handler successfully migrated
5. Documentation is complete and accurate
6. Performance is not degraded
